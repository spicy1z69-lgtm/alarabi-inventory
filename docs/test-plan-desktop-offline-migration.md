# AlArabi Inventory — خطة اختبار شاملة (Test Plan)

- **المستودع:** `spicy1z69-lgtm/alarabi-inventory`
- **الفرع المستهدف:** `desktop-offline-migration`
- **الهدف:** التحقق من مسارات المستخدم، الميزات، التكاملات، حالات الخطأ والحواف قبل تسليم نسخة Windows للعملاء.
- **الحالة:** خطة اختبار؛ الحالات لم تُعتبر ناجحة لمجرد نجاح البناء. سجّل نتيجة كل حالة عند تنفيذها.
- **قاعدة أمان:** لا تنفّذ الاختبارات على بيانات عملاء حقيقية أو مشروع Supabase الإنتاجي. استخدم حسابات وبيانات اختبار مستقلة.
- **نطاق التغيير:** لا تدمج هذا الفرع إلى `main` ولا تنشره قبل اجتياز بوابات الإطلاق.

## 1. ملخص المخاطر والقرار المعماري

يوجد تعارض يجب حسمه قبل اعتماد المنتج:
- وثيقة `docs/desktop-offline-migration.md` وREADME يصفان تطبيق Windows يعتمد على SQLite محليًا ويستمر دون الإنترنت.
- مسار التعديلات الأحدث أضاف Supabase Auth وقراءة/كتابة `app_state` أونلاين، مع كتابة نسخة محلية مرآتية. هذا **ليس إثباتًا لعمل التطبيق دون اتصال**؛ إذا كانت القراءة/الكتابة الأساسية تتطلب Supabase، فقد تتوقف الوظائف عند انقطاع الشبكة.

**قرار مطلوب قبل الإطلاق (لا تعتبره اختبارًا ناجحًا):**
1. **Desktop offline-first:** SQLite هي مصدر الحقيقة على Windows، وتعمل جميع عمليات الجرد والفواتير والخزنة دون اتصال؛ تُصمم المزامنة كميزة منفصلة بمخطط تعارضات واضح. يلزم تحديد كيف يتعامل تسجيل الدخول أول مرة مع عدم وجود إنترنت.
2. **Cloud-first:** Supabase هو مصدر الحقيقة؛ عندها يجب وصف التطبيق بوضوح بأنه يحتاج الإنترنت للوظائف السحابية، وعدم الادعاء بأنه offline.
3. إذا كان المطلوب الحسابات السحابية مع العمل المحلي دون اتصال، يلزم تصميم واختبار مزامنة ثنائية الاتجاه، معرفات ثابتة، سجل تغييرات، معالجة التعارضات وإعادة المحاولة. النسخ المحلية وحدها لا تحقق ذلك.

كما أن بيانات SQLite القديمة لا تنتقل تلقائيًا إلى حساب سحابي جديد وفق السلوك الموصوف. يجب تصميم أداة استيراد اختيارية وآمنة قبل حذف/استبدال أي بيانات قديمة.

## 3. الأدوار والبيانات الاختبارية

**الأدوار**
- زائر غير مسجل.
- مستخدم مسجل بحساب A.
- مستخدم مسجل بحساب B.
- مستخدم لديه جلسة منتهية أو رمز غير صالح.
- مستخدم يعمل دون اتصال (بعد تحديد السياسة المعمارية).

**بيانات اختبار آمنة**
- حساب A: بريد اختبار مملوك للفريق، وصنف `CON-004`، كمية ابتدائية 10.
- حساب B: بريد اختبار مختلف، وصنف بالرمز نفسه لكن وصف/كمية مختلفان.
- صنف عربي: `كونتاكتور تجريبي`; سعر شراء 100.00، سعر بيع 150.00، كمية 10.
- حالات حدودية: كمية صفر، كمية 1، كمية سالبة (إن سمح النظام)، سعر 0، كمية عشرية (إذا كانت الوحدة تسمح)، نص عربي طويل، رمز مكرر، حقول فارغة.
- فاتورة اختبار: كمية 2 × سعر 150 = 300 قبل الخصم/الضريبة؛ استخدم قاعدة الخصم والضريبة الفعلية المعرّفة في التطبيق ولا تفترضها.
- سجّل الأرصدة قبل كل اختبار وبعده، وأعد تهيئة قاعدة الاختبار بين السيناريوهات التي تتطلب ذلك.

## 4. مسارات المستخدم (User Flows)

### UF-01: عميل جديد
فتح التطبيق ← شاشة الدخول ← إنشاء حساب ← إدخال اسم المستخدم والبريد وكلمة المرور ← استجابة نجاح/طلب تأكيد البريد حسب إعدادات Supabase ← تأكيد البريد إن كان مفعلًا ← تسجيل الدخول ← شاشة النظام.
- المتوقع: لا يدخل المستخدم إلى بيانات النظام قبل وجود جلسة صالحة.
- فشل متوقع: بريد مستخدم، كلمة مرور قصيرة، بريد غير صحيح، انقطاع الشبكة، فشل إرسال التأكيد.

### UF-02: تسجيل الدخول
فتح التطبيق ← إدخال البريد وكلمة المرور ← التحقق من الجلسة ← تحميل بيانات الحساب ← استخدام النظام.
- المتوقع: تحميل بيانات المالك الحالي فقط؛ رسالة مفهومة عند فشل الدخول.
- اختبر رمزًا غير صالح، جلسة منتهية، اتصالًا بطيئًا، وتعطل Supabase.

### UF-03: استعادة كلمة المرور
اختيار «نسيت كلمة المرور» ← إدخال البريد ← إرسال رابط ← فتح الرابط على الموقع المحدد ← التحقق من رمز الاستعادة ← إدخال كلمة مرور جديدة ← نجاح ← تسجيل الدخول بالكلمة الجديدة.
- المتوقع: redirect صحيح، ولا تظهر شاشة فارغة أو خطأ `file://` في Electron.
- يجب اختبار رابط منتهي/مستخدم سابقًا، بريد غير موجود، إرسال متكرر، وفتح الرابط على جهاز/متصفح آخر.
- تأكد من إعداد Supabase Auth URL Configuration وقوالب البريد، ومن أن موقع الاستعادة المنشور يحتوي كود معالجة `PASSWORD_RECOVERY`.

### UF-04: إدارة صنف
فتح المخزون ← فتح «إضافة صنف» ← إدخال البيانات ← حفظ ← ظهور الصنف في القائمة ← فتحه وتعديله ← حفظ ← إعادة تشغيل التطبيق والتحقق.
- المتوقع: لا تختفي نافذة الإضافة عند النقر داخلها/خارجها وفق السلوك المقصود؛ لا يُفقد الإدخال دون تنبيه؛ يظهر خطأ واضح إذا فشل الحفظ.
- حذف الصنف: تأكيد قبل الحذف، ومنع حذف صنف مرتبط بحركات/فواتير إذا كانت قواعد العمل تقتضي ذلك.

### UF-05: عرض سعر
اختيار عميل/إدخال بياناته ← إضافة أصناف وكميات ← مراجعة الإجمالي ← حفظ ← إعادة فتح العرض ← طباعة A4.
- المتوقع: الإجماليات ثابتة بين الشاشة والبيانات المطبوعة، والاتجاه RTL صحيح.

### UF-06: فاتورة بيع
اختيار العميل ← إضافة أصناف ← إدخال الكمية والسعر/الخصم حسب الصلاحيات ← مراجعة الإجمالي ← حفظ مرة واحدة ← تحقق من رقم الفاتورة ← تحقق من المخزون والخزنة/المدفوعات حسب نوع السداد ← فتح الفاتورة مجددًا ← طباعة.
- المتوقع: إما نجاح جميع التغييرات المرتبطة أو عدم تطبيق أي منها؛ لا تُحفظ فاتورة مكررة عند النقر المزدوج أو إعادة المحاولة.
- اختبر فشل الشبكة/قاعدة البيانات أثناء الحفظ وعدم تطابق المخزون.

### UF-07: خزنة/دفعة
إضافة حركة قبض/صرف ← إدخال المبلغ والسبب/المرجع ← حفظ ← مراجعة الرصيد والتقرير ← إعادة التشغيل.
- المتوقع: الحركة تظهر مرة واحدة والرصيد يتغير بالاتجاه الصحيح؛ لا يقبل النظام مبلغًا غير صالح.

### UF-08: طباعة
فتح فاتورة أو عرض سعر ← اختيار طباعة ← تحديد الطابعة/الحفظ PDF ← معاينة ← طباعة/إلغاء.
- المتوقع: نافذة الطباعة لا تتجمد؛ الإلغاء لا يغيّر البيانات؛ فشل الطابعة يعرض خطأ قابلًا للفهم؛ النص العربي لا ينقلب ولا يُقص.

### UF-09: النسخ الاحتياطي والاستعادة
إنشاء نسخة احتياطية ← التحقق من وجودها وحجمها/سلامتها ← إنشاء بيانات جديدة ← عمل نسخة ثانية ← استعادة الأولى مع تحذير وتأكيد ← مراجعة الأصناف والفواتير والحركات والعلاقات.
- المتوقع: الاستعادة لا تبدأ قبل التأكيد، وتُنشأ نسخة من الحالة الحالية قبل الاستبدال، ولا ينتج عن ملف تالف مسح للبيانات الحالية.

### UF-10: إغلاق/إعادة فتح
حفظ تغيير ← إغلاق التطبيق طبيعيًا ← إعادة تشغيل ← تسجيل الدخول عند الحاجة ← التحقق من البيانات.
- المتوقع: لا فقد لبيانات أُبلغ المستخدم بنجاح حفظها.

### UF-11: انقطاع الاتصال (يتوقف الحكم النهائي على قرار المعمارية)
أثناء فتح النظام/الحفظ/تسجيل الدخول ← قطع الإنترنت ← تجربة القراءة والإضافة والحفظ والطباعة ← إعادة الشبكة.
- offline-first: عمليات الجرد والفواتير المحلية تستمر، وتظهر حالة المزامنة؛ لا تضيع العمليات بعد عودة الشبكة.
- cloud-first: تظهر رسالة صريحة ولا يُدّعى نجاح أي حفظ لم يصل إلى الخادم.
- لا يجوز عرض «تم الحفظ» قبل تأكيد طبقة التخزين المعتمدة.

## 6. حالات الخطأ العامة (Error States)

لكل عملية قراءة/كتابة/طباعة، اختبر الحالات التالية:
- انقطاع الإنترنت، DNS، timeout، وHTTP 4xx/5xx من Supabase.
- رفض الصلاحيات/RLS، جلسة منتهية، رمز استعادة غير صالح.
- فشل SQLite أو قفل قاعدة البيانات أو عدم صلاحية مجلد البيانات.
- مساحة قرص غير كافية أو ملف نسخة احتياطية للقراءة فقط.
- حقول ناقصة، قيم رقمية غير صالحة، نص طويل جدًا، رموز خاصة.
- النقر المكرر، إعادة المحاولة بعد timeout، إغلاق التطبيق أثناء العملية.
- الطابعة غير متاحة، إلغاء المستخدم، فشل إنشاء PDF.
- استجابة بطيئة: يجب إظهار حالة تحميل وتعطيل التكرار؛ لا تعرض نجاحًا قبل التأكيد.
- يجب أن تكون الرسالة للمستخدم عربية وواضحة، وأن تحتوي السجلات التقنية على correlation ID عند الإمكان، دون أسرار أو بيانات حساسة.

## 7. قواعد سلامة البيانات المحاسبية

هذه ثوابت يجب اختبارها بعد كل عملية:
1. لا يتكرر رقم الفاتورة/العرض أو سجل الدفعة بسبب النقر المزدوج أو retry.
2. مجموع البنود = مجموع الكميات × أسعارها، مع تطبيق الخصومات والضرائب وفق القواعد المعرفة.
3. المخزون بعد الحركة = المخزون السابق + الوارد - الصادر؛ لا يحدث تعديل مزدوج.
4. رصيد الخزنة = الرصيد السابق + المقبوضات - المصروفات وفق نموذج الحساب المعتمد.
5. الدفعة الجزئية/الكاملة لا تتجاوز قيمة الفاتورة إلا إذا كانت سياسة المنتج تسمح بذلك.
6. فشل معاملة مركبة يجب ألا يترك فاتورة محفوظة دون حركة المخزون/الدفعة المطلوبة.
7. حذف أو إلغاء المستند يعكس أثره مرة واحدة فقط ويحافظ على سجل التدقيق حسب السياسة.
8. الحساب A لا يقرأ أو يعدل سجلات الحساب B.
9. كل عملية تظهر نجاحًا يجب أن تبقى بعد إعادة تحميل/تشغيل النظام.
10. لا تستبدل بيانات قائمة ببيانات افتراضية عند فشل التحميل.

## 9. بوابات الإطلاق (Release Gates)

لا تعتبر النسخة جاهزة للتسليم حتى تتحقق كلها:
- [ ] بناء الويب ناجح.
- [ ] إنشاء Windows installer ناجح على Windows ورفع artifact قابل للتنزيل.
- [ ] تثبيت نظيف وتشغيل/إغلاق/إعادة فتح ناجح على Windows مدعوم.
- [ ] جميع حالات P0 ناجحة؛ لا توجد عيوب P0/P1 مفتوحة تؤثر على المال أو الخصوصية أو فقد البيانات.
- [ ] التسجيل والدخول والخروج واستعادة كلمة المرور مجربة end-to-end باستخدام البريد الحقيقي الاختباري.
- [ ] اختبار عزل حساب A وB ناجح مع فحص RLS من جهة الخادم.
- [ ] إضافة صنف، حفظ فاتورة، تحديث المخزون/الخزنة، إعادة فتح وطباعة ناجحة.
- [ ] النسخ الاحتياطي والاستعادة اختُبرا عمليًا على نسخة اختبار.
- [ ] قرار offline/cloud موثق ومتوافق مع السلوك الفعلي؛ لا تسويق كـoffline إذا كانت العمليات تتطلب Supabase.
- [ ] سياسة نقل البيانات القديمة موثقة، ولا يحدث خلط بين عميل وآخر.
- [ ] مراجعة التبعيات والأسرار وسياسات redirect والصلاحيات.
- [ ] لا يتم الدمج إلى `main` أو النشر قبل موافقة المراجعة.

## 11. الأولويات المقترحة للتنفيذ

1. احسم قرار SQLite offline-first مقابل Supabase cloud-first؛ لا تختبر مطلبًا متناقضًا.
2. اختبر P0: build/installer، auth/recovery، عزل الحسابات/RLS، حفظ الفاتورة وتناسق المخزون والخزنة، الطباعة، backup/restore.
3. أصلح جميع حالات الفشل مع رسائل مرئية، ثم أعد تشغيل الاختبارات المتأثرة واختبارات regression.
4. نفّذ حالات P1 للميزات والحواف، ثم الأداء والأمان.
5. اجعل نتائج الاختبار موثقة على commit محدد قبل أي إصدار.

**تنبيه:** هذه الوثيقة تحدد الخطة والنتائج المتوقعة؛ لا تعني أن كل الاختبارات نُفذت. نجاح `npm run build` وحده لا يثبت صحة التكاملات أو حفظ البيانات أو جاهزية مثبت Windows.

## 12. اختبارات الحساب المحلي للنسخة المكتبية

هذه الحالات أُضيفت بعد فصل مصادقة Windows عن Supabase؛ **لم تُنفّذ عمليًا بعد**:

| ID | الإجراء | النتيجة المتوقعة |
|---|---|---|
| LOCAL-AUTH-01 | أول تشغيل على قاعدة جديدة | تظهر شاشة إنشاء اسم المستخدم وكلمة المرور دون طلب بريد أو إنترنت |
| LOCAL-AUTH-02 | كلمة مرور أقل من 10 أحرف أو غير متطابقة | رفض الإنشاء برسالة واضحة |
| LOCAL-AUTH-03 | إنشاء الحساب الأول ثم إعادة التشغيل | لا تظهر شاشة الإنشاء مرة أخرى؛ يطلب تسجيل الدخول |
| LOCAL-AUTH-04 | كلمة مرور خاطئة | رفض الدخول برسالة عامة، وعدم فتح بيانات المخزون |
| LOCAL-AUTH-05 | فحص جدول `local_users` | لا توجد كلمة مرور نصية؛ يوجد salt وبصمة مشتقة باستخدام scrypt |
| LOCAL-AUTH-06 | تسجيل الخروج ثم استدعاء IPC الخاص بالبيانات | تُرفض القراءة والكتابة والطباعة حتى تسجيل الدخول مجددًا |
| LOCAL-AUTH-07 | حفظ أصناف وفواتير ثم إغلاق التطبيق وإعادة فتحه | تبقى البيانات بعد تسجيل الدخول |
| LOCAL-AUTH-08 | التحقق من طلبات الشبكة أثناء الدخول المحلي والحفظ | لا يجري تسجيل دخول Supabase ولا قراءة/كتابة `app_state` السحابية من مسار desktop |
| LOCAL-AUTH-09 | بيانات قديمة في `app_state` بلا `owner_id` | تبقى معزولة في جدول legacy؛ لا تُنسب تلقائيًا إلى الحساب المحلي |
| LOCAL-AUTH-10 | اختبار الويب في المتصفح | يبقى تسجيل الدخول والتسجيل السحابي كما كانا، ولا يتغير مسار الويب |
| LOCAL-AUTH-11 | اختبار الطباعة من الحساب المحلي | تفتح نافذة الطباعة فقط بعد المصادقة المحلية |
| LOCAL-AUTH-12 | اختبار بناء وتثبيت Windows على قاعدة جديدة وقاعدة قديمة | لا فقد بيانات، ولا أخطاء ترحيل أو تشغيل |

**ملاحظة:** بيانات النسخة المكتبية محلية على نفس الكمبيوتر. هذا الحساب ليس حسابًا سحابيًا، ولا يمكنه تسجيل الدخول إلى موقع الويب أو استرجاع كلمة مروره عبر البريد. يجب اختبار مسار الخروج والدخول والطباعة والحفظ فعليًا على Windows قبل تسليم النسخة.
